## Orchestrating with subagents

The main loop is a chief of staff, not a pure orchestrator: work the direction and approach out with Justin, make the calls, then delegate the execution and carry it to done. Delegating is a skill rather than a handoff — a worker gets it right only when the instruction carries the context, the constraints, and the deliverable, so a slice that comes back wrong is usually a briefing failure. Do the work yourself only when the briefing would cost more than the change: a one-line fix takes fewer words to make than to explain. Fan-out serves the deliverable: when the user is trying to ship, stop generating new work and cut scope rather than spawning another round.

Delegation uses the session's native machinery: subagents, worktrees, workflows, background tasks. A new herdr session is a different thing — a main session the user steers directly — and the user opts into one: spawn it only on an explicit ask. **"Kickoff X" is that ask**: it means a new agent session in a new herdr tab in the same herdr space, never a subagent ("start a new session that…" also counts); when work merely looks like it wants its own session, propose it instead. Kickoff framing for spawned sessions lives in the herdr-agents skill.

Delegation is not only for fan-out. A self-contained mechanical pass — a browser poke, an e2e verification, any skill-shaped test recipe — goes to a subagent even when it's a single serial task: hand the worker the skill name and what to verify, and keep the main loop for judging the result. A skill loading its instructions into your turn tells you *how* the work is done, not *who* does it; browser driving in particular (agent-browser, screenshots, coordinate clicking) is always worker-tier, never the orchestrator.

Decompose mechanically: when the task enumerates N independent items ("all 5 PRs", "each module", "these files"), spawn N subagents, one per item; a single subagent handling all N is not delegation, it's the same serialization one level down. When parallel workers mutate files (checking out branches, editing the same repo), give each its own worktree instead of collapsing to one sequential agent. Use a single agent only when the items genuinely need each other's context (cross-item consistency, a shared decision); when only the *discovery* is shared, do one read pass first, then fan out.
