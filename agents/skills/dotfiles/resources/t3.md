# T3

Owns how T3 Code updates and how the headless server's systemd user service is configured; `setup_t3` in install.sh. Which machine runs it and under which user is in the `dev-machines` skill, not here.

## Updating

`update_t3` updates the desktop package on Arch and macOS. On Ubuntu, it runs `t3 service update`, which installs the CLI version as the pinned runtime and repoints `t3code.service` at it. When the installed runtime already matches, it does nothing, and that no-op is what makes the Ubuntu daily timer safe: an unchanged day never restarts the server.

The desktop app owns its local server, so updating its package updates both. The Ubuntu timer and a manual run execute the same script, so the server paths cannot drift.

```
update_t3                                    # update this machine now
systemctl --user list-timers t3code-update   # Ubuntu: next timer fire
journalctl --user -u t3code-update -n 50     # Ubuntu: what the last run did
```

On Ubuntu, a bad nightly is the launcher's problem: it trial-boots the new version and rolls back to the previous one if the boot fails.

## The unit is regenerated, so config goes in a drop-in

Every `service update` rewrites `t3code.service` from a fixed template. Anything added to the unit file is erased by the next update. Put it in `~/.config/systemd/user/t3code.service.d/override.conf`.

That is why the VPS gets a drop-in: `write_t3_bind_dropin` in install.sh binds the server to the Tailscale address from `tailscale ip -4` instead of the loopback default, via `T3CODE_HOST`. It also restores the `tailscaled.service` ordering the template drops, because binding that address before tailscaled is up fails. The drop-in relies on the launcher passing its environment through to the server child; if the bind stops applying after an update, check that first.

install.sh regenerates the drop-in on every run (writing it only when the content changed) and reloads units, but never restarts `t3code.service`, so a changed bind takes effect only after a restart of that service. Restarts on the VPS are approval-gated; see the `dev-machines` skill.

The env vocabulary (`T3CODE_HOST`, `T3CODE_PORT`, `T3CODE_MODE`, and the rest) is the config schema inside the CLI bundle. Grep for `T3CODE_` in `dist/bin.mjs` under the installed version dir in `~/.t3/runtime/versions/`. The unit renderer is `renderBootServiceUnit` in the same bundle.

## Where things live

`~/.t3` is `T3CODE_HOME`. `runtime/` holds the launcher, the pinned version dirs (each with a `.install-complete` sentinel), and `service-state.json`, which names the active version. `userdata/` holds the sqlite database, settings, secrets, and `logs/boot-service.log`.

State lives in `userdata/`, so re-running `t3 service install` against the same `T3CODE_HOME` keeps every project and session.
