# T3

Owns how T3 Code updates and how its systemd user service is configured; `setup_t3` in install.sh. Which machine runs it and under which user is in the `dev-machines` skill, not here.

## Updating

`update_t3` updates the desktop package on Arch and macOS. On Ubuntu, a fresh machine installs the background service from the exact current nightly; an existing machine runs `t3 update <version> --yes`. The explicit version avoids a stale `npx` dist-tag cache, and `--yes` permits an unattended service restart when the version changes. An unchanged day remains a no-op.

On sfx, updating the desktop package updates only the GUI; the standalone server keeps its installed version. Automatic T3 updates on sfx are deferred. The Ubuntu timer and a manual run execute the same script, so the server paths cannot drift.

```
update_t3                                    # update this machine now
systemctl --user list-timers t3code-update   # Ubuntu: next timer fire
journalctl --user -u t3code-update -n 50     # Ubuntu: what the last run did
```

On Ubuntu, a bad nightly is the launcher's problem: it trial-boots the new version and rolls back to the previous one if the boot fails.

## Service config goes in a drop-in

T3 owns `t3code.service` and may regenerate it during an install, repair, or update. Anything added to the unit file can be erased. Put local service configuration in `~/.config/systemd/user/t3code.service.d/override.conf`.

`write_t3_service_dropin` in install.sh keeps an existing Arch service on loopback and binds Ubuntu to its Tailscale address via `T3CODE_HOST`. Ubuntu also gets `tailscaled.service` ordering because binding that address before tailscaled is up fails. The shared `PATH` mirrors the user-level install locations in `zshrc`, so the service can find provider CLIs such as Codex without per-provider binary overrides. The drop-in relies on the launcher passing its environment through to the server child; if the bind or provider discovery stops applying after an update, check that first.

install.sh configures existing Arch services and installs the service on a fresh Ubuntu host. It writes the drop-in only when content changed and reloads units. It leaves an existing `t3code.service` running, so changed service environment takes effect only after a restart. Restarts on the VPS are approval-gated; see the `dev-machines` skill.

Use the active runtime's `--help` output as the current command and environment schema; nightly runtime packaging has changed between JavaScript bundles and self-contained executables.

## Where things live

`~/.t3` is `T3CODE_HOME`. `runtime/` holds the launcher, the pinned version dirs (each with a `.install-complete` sentinel), and `service-state.json`, which names the active version. `userdata/` holds the sqlite database, settings, secrets, and `logs/boot-service.log`.

State lives in `userdata/`, so re-running `t3 service install` against the same `T3CODE_HOME` keeps every project and session.

## T3 Connect is machine-local

T3 Connect authorization is saved under `~/.t3/userdata`; it is not dotfiles configuration. Link a new headless host once with `t3 connect link`, then inspect saved setup with `t3 connect status` and the background service with `t3 service status`. A link provisioned by the desktop can remain valid even when CLI status reports exposure or authorization as false. Verify live relay connections in `~/.t3/userdata/logs/boot-service.log` and remote client access before deciding a host needs re-linking.
